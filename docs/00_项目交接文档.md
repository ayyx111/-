## 一、项目概览

### 1.1 产品简介
「校园版咸鱼」是面向在校大学生的 **C2C 二手交易 + AI 内容审核/智能推荐** 平台。提供注册登录、校园身份认证、商品发布/浏览/搜索、收藏/下单/订单履约、站内私信、管理员后台审核、AI 商品内容审核、AI 智能推荐等能力。

### 1.2 技术栈总览
| 层级 | 技术选型 | 关键说明 |
|---|---|---|
| 前端 | Vue 3 + Vite 5 + Pinia 2 + Vue Router 4 + Element Plus 2.8 + Axios 1.7 | 组件按需加载(自动引入)；SCSS 样式 |
| 后端（主服务） | Node.js 18+，Express 4.19，Sequelize 6.37 ORM，Socket.IO 4.7，Multer 1.4，JWT (jsonwebtoken 9)，bcryptjs 2.4，CORS + Helmet + Rate Limit | 同时兼容 **SQLite / MySQL / PostgreSQL** 三种数据库 |
| 数据库 | 开发：SQLite 或本地 MySQL；**生产：Railway PostgreSQL**（已启用公共网络访问）| Sequelize 自动建表 + 启动时增量补列 |
| 图片存储 | **Railway 容器本地磁盘**（免费），Express `static` 暴露 `/uploads/`，配合公网域名生成绝对 URL | ⚠️ Redeploy 会清空（免费方案） |
| AI 服务 | Python FastAPI 独立服务（`ai-service/`）：LLM 内容审核 + 智能推荐 + 语义搜索 + 客服机器人 | HTTP 调用，主后端通过 `AI_SERVICE_URL` 接入 |
| 部署/CI | GitHub → GitHub Actions → **IGA Pages 部署前端**；后端部署到 **Railway**（含 PostgreSQL 插件 + 环境变量） | 每次 push main 自动部署前端 |

## 二、环境变量完整对照表

> 生产部署 **只看这一节就能对照补齐**。

### 2.1 后端（Railway → backend Service → Variables）

| 变量名 | 推荐值 | 必填 | 用途 | 备注 |
|---|---|---|---|---|
| `NODE_ENV` | `production` | ✅ | 运行模式，控制 JWT 强校验等 | |
| `PORT` | 留空让 Railway 注入 | - | HTTP 端口 | 必须监听 `$PORT`，本项目自动读 process.env.PORT |
| `DB_TYPE` | `postgres` | ✅ | Sequelize 方言选择 | 只能是 `postgres`/`mysql`/`sqlite` |
| `DATABASE_URL` | 使用 Railway 变量引用 **`${{Postgres.DATABASE_URL}}`**（推荐）或 PG 插件的 Public URL | ✅ | 数据库连接 | 用 `{PGHOST}` 等拆开也行 |
| `DB_SYNC` | `true` | ✅（首次） | 启动时 `sequelize.sync({alter:false})` 建表 + `ensureSchemaColumns` 补列 | 表结构稳定后可改为 `false` |
| `JWT_SECRET` | 一段随机 32+ 字符，**不可**含 `change_me` | ✅ | AccessToken 签名密钥 | 含 `change_me` 启动直接退出（[config/index.js](backend/src/config/index.js#L84-L89)） |
| `JWT_REFRESH_SECRET` | 另一段随机串 | ✅ | RefreshToken 签名密钥 | |
| `JWT_ACCESS_EXPIRES` | `7200` | - | AccessToken 秒 | 默认 2 小时 |
| `JWT_REFRESH_EXPIRES` | `604800` | - | RefreshToken 秒 | 默认 7 天 |
| `UPLOAD_DIR` | `uploads` | - | 容器内上传目录 | 用 express.static 暴露 |
| `UPLOAD_MAX_SIZE` | `5242880` | - | 5MB | |
| `UPLOAD_URL_PREFIX` | `/uploads` | - | 静态资源 URL 前缀 | app.js 中 `app.use('/uploads', static(...))` |
| **`UPLOAD_PUBLIC_BASE_URL`** | **`https://resplendent-caring-production-ebd2.up.railway.app`** | **✅ 生产关键** | 图片返回的公网绝对 URL 前缀，其他电脑/IGA Pages 必须有 | 不设置 → 图片只返回相对路径 `/uploads/xxx` → IGA Pages 打不开图片 |
| `CORS_ORIGIN` | `*` | - | 生产环境允许前端来源 | 严格场景可写为 `https://<pages 域名>` |
| `ADMIN_USERNAME` | `admin` | - | 首次启动初始化管理员账号用户名 | |
| `ADMIN_PASSWORD` | `admin123`（首次）或自定强密码 | - | 首次启动初始化管理员密码 | 后续改密码改这里无效，需进 DB |
| `AI_SERVICE_URL` | 留空或 AI 微服务公网地址 | - | AI 审核/推荐地址 | 留空会降级为本地规则（无 AI 能力） |
| `RATE_LIMIT_LOGIN_MAX` | `5` | - | 登录限流/分钟 | |
| `RATE_LIMIT_GENERAL_MAX` | `100` | - | 通用限流/分钟 | |

**变量校验**：`NODE_ENV=production` 时若 `JWT_SECRET` 含 `change_me` 字样，后端进程**立即退出 1**（见 [config/index.js](backend/src/config/index.js#L84-L89)）。

## 四、生产部署与 CI/CD

### 4.1 前端：GitHub Actions → IGA Pages 自动部署
- 工作流：`.github/workflows/deploy-to-iga-pages.yml`
- 触发：`git push origin main`
- 步骤：
  1. Checkout
  2. Node setup + `cd frontend && npm ci && npm run build`
  3. 输出目录：`frontend/dist`
  4. IGA Pages Deploy（使用 GitHub Secrets 中已配置的 `IGA_ACCESS_KEY_ID` / `IGA_SECRET_ACCESS_KEY`）
- 结果：在 **GitHub Actions → Deploy to IGA Pages → build summary** 查看最新前端访问 URL
- **关键**：构建阶段会优先读取 **GitHub Variables** 的 `VITE_API_BASE_URL`，缺失时 fallback 到仓库内 `frontend/.env.production` 的硬编码 Railway 公网地址

### 4.2 后端：Railway 手动部署流程
本项目使用 Railway 部署 **backend service + Postgres plugin**，步骤如下：

1. **新建空 Project**，连接 GitHub 仓库 → 选择 backend **子目录**部署（或选择整仓 + `Root Directory=backend`）
2. **添加 Postgres 插件**：Project → Add Service → Database → Add PostgreSQL
3. **backend Service → Variables**：按 **2.1 节表格**全部填完
   - `DATABASE_URL` 建议填 `${{Postgres.DATABASE_URL}}`
   - **必须**加上 `UPLOAD_PUBLIC_BASE_URL=https://<你的后端 public domain>`（在 backend → Settings → Networking → Public Network 能看到域名）
   - 改完 Variables 会自动 Redeploy
4. **Settings → Networking → Expose on public network**：勾选 backend + postgres（postgres 方便本地用 DBeaver 连）
5. **Healthcheck**：backend Settings 里配置 `/health`，超时 30s
6. 等待 Deploy Logs 出现 `[Server] 启动成功,端口=xxxx` 即可

## 五、API 与上传契约（最常用）

> 完整契约见 `docs/05_API接口设计文档.md`，这里只列跨环境部署后容易出错的部分。

### 5.1 API 基础
- 前缀：`/api/v1`
- 鉴权：登录后 `Authorization: Bearer <accessToken>`
- 响应格式：
  ```json
  { "code": 200, "message": "成功", "data": { } }
  ```
  前端 axios 已在 [request.js](frontend/src/api/request.js) 拦截器统一返回 `res.data.data`，并在非 200 时 `ElMessage.error(message)` 然后 `Promise.reject`。

### 5.2 图片上传（极容易出错，请严格按契约）
后端路由：
- `POST /api/v1/upload/image` → **单张**，multer `single('file')` → FormData 字段名 **`file`**
- `POST /api/v1/upload/images` → **批量**，multer `array('images', 9)` → FormData 字段名 **`images`**

返回：
```json
{
  "code": 200,
  "data": {
    "url": "https://resplendent-caring-production-ebd2.up.railway.app/uploads/202608/1660000000_ab12cd.jpg",
    "filename": "1660000000_ab12cd.jpg",
    "size": 123456,
    "mimetype": "image/jpeg"
  }
}
```

前端调用：
- **严禁** `el-upload :action="/api/v1/upload/image"`（IGA Pages 静态域下会 404）
- **必须**用自定义上传 `:http-request="customUpload"` → 调 `productApi.uploadImage(formData)` → axios 封装（自带 baseURL、token、拦截器）
- **严禁**手动写 `Content-Type: multipart/form-data`（Axios + 浏览器自动带 boundary；手动覆盖会导致 Multer 无法解析边界，其他浏览器/电脑必挂）
- 参考：[Create.vue customUpload](frontend/src/views/product/Create.vue#L79-L120)

### 5.3 校园认证
- 新流程：**学生证照片为可选项**
- `POST /api/v1/auth/verify-campus`，JSON body：
  ```json
  { "school": "示例大学", "college": "示例学院", "enrollmentYear": 2024, "campusProof": "" }
  ```
- `is_verified` 状态：`0=未提交 / 2=待审核 / 1=已通过 / 3=未通过`
- 前端**允许待审核(2)发布商品**，参考 [stores/user.js](frontend/src/stores/user.js) 中 `isVerified()`

### 5.4 健康检查
`GET /health` → 200 OK，用于 Railway healthcheck。

## 六、数据模型与自动建表

### 6.1 Sequelize 自动表同步
- 启动时执行 `sequelize.sync({ force: false })`（DB_SYNC=true 时开启）
- `force:false` 不会删除数据，但**不会自动修改已存在表的列** → 所以 [app.js](backend/src/app.js#L175-L233) 中写了 `ensureSchemaColumns()`：对每个 Model 定义中出现的列，对比 PG `information_schema.columns`，缺失的自动 `ALTER TABLE "xxx" ADD COLUMN "yyy" TYPE ...`，支持 PostgreSQL 映射（TINYINT→SMALLINT 等）

## 七、常见问题排查（FAQ）

> 以下是历史踩过的所有坑，接手同学按清单排查即可。

### Q1 前端 IGA Pages 上能打开页面但登录/接口全报 404 / "请求的资源不存在"
**原因**：`VITE_API_BASE_URL` 没有注入到构建产物，前端请求发到了 IGA Pages 服务器而不是 Railway 后端。
**排查**：
1. 浏览器 DevTools → Network → 查看请求 URL：应该是 `https://resplendent-caring-production-ebd2.up.railway.app/api/v1/...`，而不是 `https://*.pages.on-iga.com/api/v1/...`
2. 若 URL 错 → 检查：
   - GitHub Variables 是否设置 `VITE_API_BASE_URL=https://resplendent-caring-production-ebd2.up.railway.app/api/v1`
   - 或 `frontend/.env.production` 里硬编码的地址是否正确
3. 确认 Actions build 日志里 echo `VITE_API_BASE_URL=$VITE_API_BASE_URL` 能输出正确值

### Q2 上传图片成功，但是其他电脑打开商品看不到图片（图片 404）
**原因**：后端未设置 `UPLOAD_PUBLIC_BASE_URL`，返回的 URL 是 `/uploads/xxx` 相对路径，IGA Pages 访问相对路径会找 IGA Pages 静态服务器。
**修复**：Railway backend Service → Variables → 添加：
```
UPLOAD_PUBLIC_BASE_URL=https://resplendent-caring-production-ebd2.up.railway.app
```
然后 Redeploy。上传返回的 URL 会变为绝对路径（带 Railway 域名），所有电脑都能直接访问。

### Q3 其他电脑上传图片失败（本机能）
**排查清单**：
1. **确认 Content-Type 没手动写**：Axios 上传 FormData 时**绝对不要**手动 `headers:{'Content-Type':'multipart/form-data'}`，会破坏浏览器自动生成的 boundary，导致 Multer 解析失败（不同浏览器行为不一致 → 本机成功其他电脑失败）
2. 检查 `VITE_API_BASE_URL` 是否正确指向 Railway 公网
3. Railway backend `UPLOAD_PUBLIC_BASE_URL` 是否已设（否则"其他电脑图片显示失败"被用户当成上传失败）

### Q4 Railway Build 日志：`npm error code 1`，better-sqlite3/sqlite3 node-gyp rebuild 失败
**原因**：Railway 默认 Node 18，better-sqlite3/sqlite3 需要更高 Node + 编译 Python 工具链；且生产已改用 Postgres，SQLite 依赖完全不需要。
**修复**（已做）：`backend/package.json` dependencies 中删除 `better-sqlite3` 和 `sqlite3`，并删除对应 `package-lock.json` entries。

### Q5 Railway Deploy Logs 报 `column "ai_review_reason" does not exist` / `type "tinyint" does not exist`
- **tinyint**：PostgreSQL 不支持 MySQL TINYINT，模型里要用 `DataTypes.SMALLINT`（本项目已全部替换）
- **缺列**：启动时 `ensureSchemaColumns()` 会自动 `ALTER TABLE` 补列；若仍报错 → 确认 `DB_SYNC=true` 或手动重启一次后端容器触发补列逻辑

### Q6 前端控制台 `Object prototype may only be an Object or null: undefined`（Pinia 报错）
**原因**：pinia-plugin-persistedstate + destr 与版本不匹配。
**修复**（已做）：降级 pinia / pinia-plugin-persistedstate 到锁定版本并改为自定义 localStorage 持久化。遇到后清浏览器 `localStorage` 并强刷即可。

### Q7 点「获取验证码」没反应 / 收不到倒计时
**原因**：原 catch 静默吞错。当前已修：获取验证码接口会正确倒计时+详细错误提示。

### Q8 Railway Redeploy 后上传的图片全没了
**免费方案正常现象**：免费图片用的是 Railway 容器本地磁盘（`uploads/`），每次 Redeploy 会用新建镜像重启容器 → 磁盘重置 → 图片丢失。
- **缓解**：演示前一次性上传，不要频繁 Redeploy
- **升级方案**（免费 10GB 可持久化）：Cloudflare R2 / 腾讯云 COS 免费额度 → 改造 uploadController 上传到 S3/R2，返回 CDN URL

### Q9 其他同学如何一起管理仓库 + 获取最新 IGA 链接？
1. GitHub → 项目 Settings → Collaborators → 邀请同学（写权限）
2. 所有 Push main 的人都会触发 Actions 重新部署
3. 最新链接统一在 **GitHub Actions → Deploy to IGA Pages → 最近一次成功的 workflow → build summary** 获取；也可以把链接放到仓库 README 里人工维护

### Q10 校园认证页面顶部显示"您已通过校园认证"但下方还是表单
**原因**：`is_verified` 后端返回的是 snake_case（`is_verified`），前端旧代码用 camelCase（`isVerified`）判断，导致始终 false。
**修复**（已做）：后端 `sanitizeUser` 同时输出 snake_case + camelCase 两套字段，前端 `verifyStatus` 优先读 `is_verified`；待审核状态(2)也视为"已完成认证步骤"可发布商品，避免用户卡住。
遇到缓存：清 `localStorage` 后重新登录即可。

### Q11 数据库连接错误 `getaddrinfo ENOTFOUND postgres.railway.internal`
**原因**：用了 Railway 内网域名（`*.railway.internal`），但 backend 与 Postgres plugin 的网络不对等/需要公共网络。
**修复**（已做）：Postgres plugin → Connect → 切换到 **Public Network**，用 Public DATABASE_URL；或使用 `${{Postgres.DATABASE_URL}}` 变量引用。

## 八、运维手册

### 8.1 日常重启/发布
- **前端**：`git push origin main` → 等 GitHub Actions 完成（约 2~3 分钟）→ Summary 获取新链接
- **后端**：改代码 push 后 Railway 自动 Redeploy；或手动点击 backend → Deployments → 当前版本右上角「Redeploy」

### 8.2 紧急后端日志
Railway → backend Service → **Deploy Logs**（部署期错误）与 **Build Logs**（构建期错误）。
- 健康检查失败：先看 Deploy Logs 是否有 `[启动失败]`、`MODULE_NOT_FOUND`、`column xxx does not exist` 等关键词
- 数据库错误：优先看 `[DB]` 开头的日志（在 app.js 启动阶段）

### 8.3 图片清理 / 容量
Railway 容器约 50GB 可写空间，`uploads/` 目录存放。目前无清理策略；可在后端加一个 `cron` 脚本按 TTL 删除旧文件（目前课程作业不需要）。

### 8.4 安全建议（生产/演示前必做）
1. 修改 `JWT_SECRET` 为随机长串（不要带 `change_me`）
2. 修改 `ADMIN_PASSWORD` 为强密码（首次启动后需要改 DB 中 admins 表）
3. 把 `CORS_ORIGIN` 限制为具体前端域名
4. Postgres Public 网络仅在需要本地客户端连接时开启；长期只允许内网更好
